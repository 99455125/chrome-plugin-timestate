# 从零开发 Chrome 日报工时统计插件

适用版本：`2.0.0`

这份文档的目标不是介绍结果，而是带你“重新做一遍”。如果你完全照着这份文档做，应该可以独立开发出当前这个插件。

## 1. 先建立正确认知

你做的不是普通前端页面，而是“浏览器插件 + 老系统页面联动”项目。

它有 4 个运行环境：

1. popup 页面
2. background service worker
3. content script
4. 业务系统 iframe 页面

你之后所有问题，几乎都能归结为一句话：

“当前这段代码运行在哪个环境里？”

## 2. 第一步：先不要写插件，先把页面搞清楚

先研究这些样本文件：

- `总体页面.html`
- `my_report.jsp页面`
- `点击我的日报 my_report.jsp请求与响应`
- `未登录页面结构`
- `未登录 iframe`

你要先确认 5 件事：

1. 主页面是不是 iframe 架构
2. “我的日报”是怎么进入的
3. 查询表单有哪些字段
4. 搜索按钮是什么
5. 结果表格的列名是什么

做完这一步，你应该知道：

- iframe 的选择器
- 开始日期输入框
- 结束日期输入框
- 搜索按钮
- 工时列表头文字
- 日报日期列表头文字

如果这一步没搞清楚，不要急着写代码。

## 3. 第二步：先写解析器，不要先写 UI

这一阶段目标只有一个：给我一份 HTML，我能算出总工时。

### 3.1 为什么先写解析器

因为 UI 做得再漂亮，如果统计不准，整个项目就是失败的。

### 3.2 解析器要实现什么

建议先实现：

1. 找到 `#maintable`
2. 读取表头
3. 动态找到 `用时(H)` 列
4. 遍历 `tbody tr`
5. 统计总工时

然后再逐步补：

1. 记录条数
2. 出勤天数
3. 每日工时聚合
4. 登录页检测
5. 无效工时检测
6. 结构化日报明细提取
7. AI 提示词生成所需数据

### 3.3 为什么不要写死列号

不要写：

```js
cells[6]
```

要写：

```js
const hoursIndex = headers.findIndex(...)
```

这是从“临时脚本”到“可维护代码”的关键一步。

### 3.4 建议你先写成纯函数

像这样：

```js
export function parseWorkHours(html) {
  // 输入 html，返回统计结果
}
```

这样它可以单独测试，不依赖 popup，不依赖 content script。

## 4. 第三步：把日期工具独立出去

这一步很简单，但很值。

把“上月”和“当月”的日期计算单独放到一个文件，比如：

- `lib/date-range.mjs`

原因是：

1. popup 和悬浮窗都要用
2. 日期逻辑不应该散落在 UI 代码里
3. 后面如果要加“本周”“本季度”会很方便

## 5. 第四步：搭最小可运行插件骨架

这时候再创建：

- `manifest.json`
- `popup.html`
- `popup.js`
- `background.js`
- `content.js`

### 5.1 manifest 最少要配什么

1. `manifest_version: 3`
2. `action.default_popup`
3. `background.service_worker`
4. `content_scripts`
5. `permissions`
6. `host_permissions`

### 5.2 先只做最小功能

这个阶段不要一口气做完全部。

建议第一版目标只有：

1. 点击 popup 按钮
2. background 能收到消息
3. content script 能收到 background 转发的消息

只要这条消息链路通了，后面都好做。

## 6. 第五步：写消息通信

建议先记住这个职责分工：

### popup 负责

- 用户点击
- 调用 background
- 渲染结果

### background 负责

- 统一入口
- 注入脚本
- 调度页面执行
- 调用解析器

### content script 负责

- 真正操作业务页面

### 最常见消息流

```text
popup -> background -> content script -> background -> popup
```

这是这个项目的主通信链路。

## 7. 第六步：在页面里找到 iframe 和日报页

这一步开始进入真正难点。

你要写一个函数，做 3 件事：

1. 找到 iframe
2. 进入 iframe 文档
3. 判断当前 iframe 是什么页面

建议把结果抽象成：

```js
{
  state: "report" | "login" | "other",
  reportWindow,
  reportDocument,
  iframeElement
}
```

这样后面逻辑就会非常清晰。

## 8. 第七步：实现自动进入“我的日报”

不要要求用户先手动点进去，插件应该自己做。

可行方案有两种：

1. 找左侧链接，真实点击
2. 如果点不到，就直接改 iframe 的 `src`

你在这个项目里最好两个都做：

1. 优先点击真实链接，体验更像用户操作
2. 点击失败时再回退到直接设 `iframe.src`

## 9. 第八步：自动填写表单并点击搜索

这一步不要只赋值：

```js
input.value = "2026-03-01"
```

建议补上事件：

```js
input.dispatchEvent(new Event("input", { bubbles: true }))
input.dispatchEvent(new Event("change", { bubbles: true }))
```

因为老系统有时候会监听这些事件。

触发查询时，优先：

1. `button.click()`
2. `form.requestSubmit()`
3. `form.submit()`

这是比较稳的顺序。

## 10. 第九步：等待 iframe 刷新

点击查询后不能立刻读表格，必须等 iframe 重新 load。

所以你要写一个：

```js
waitForIframeLoad(iframe, timeout)
```

要点：

1. 监听 `load`
2. 设置超时
3. load 后稍微等几十到几百毫秒再读文档

否则你会遇到：

- iframe 已加载但 DOM 还没稳定
- 读取内容为空
- 页面正在重定向

## 11. 第十步：解决“只统计第一页”的问题

这一步是整个项目最关键的地方。

### 错误思路

刷新完页面后，直接：

```js
document.querySelectorAll("#maintable tbody tr")
```

这通常只能拿当前页。

### 正确思路

在 iframe 刷新完成后，用 iframe 自己的 `window.fetch` 再发一次同样的 POST，请求完整 HTML。

原因：

1. 会话沿用当前页面
2. 请求上下文更稳定
3. 你拿到的是完整返回，不受前端分页影响

也就是说：

- 页面刷新是为了用户体验
- 二次 fetch 是为了数据完整

## 12. 第十一步：background 中接入解析器

此时 content script 已经能返回完整 HTML。

下一步在 background 里：

1. 调用 `parseWorkHours(html)`
2. 把 `startDate`、`endDate`、`fetchedAt` 拼进去
3. 存到 `chrome.storage.local`
4. 返回给 popup

建议 background 返回结构统一一点，例如：

```js
{
  totalHours,
  rowCount,
  attendanceDayCount,
  dailyHoursMap,
  reportEntries,
  aiSummaryPrompt,
  startDate,
  endDate,
  fetchedAt
}
```

这里新增的两个字段分别用于：

1. `reportEntries`
   保存每条日报的项目名称、分类、内容、日期、单条工时等明细，后续给 AI 汇总和日历详情复用。

2. `aiSummaryPrompt`
   后台统一生成的 AI 月报提示词。悬浮窗点击 `AI生成日报` 时直接使用它，不自己在页面里重新拼字符串。

## 13. 第十二步：做 popup 结果展示

现在才开始认真做 UI。

popup 第一版建议只展示：

1. 时间范围
2. 总工时
3. 出勤天数
4. 记录条数
5. 统计时间

先别急着加太多花活，因为 popup 的核心职责是“快捷入口”。

## 14. 第十三步：做错误处理

这一步非常重要，很多新手会忽略。

你至少要单独处理这些错误：

1. 当前标签页不是业务系统页面
2. 没找到主页面 iframe
3. 当前会话失效，跳到登录页
4. 没找到查询表单
5. 等待 iframe 刷新超时
6. 页面结构变化，没找到表格
7. 工时列不存在
8. 页面脚本没注入成功
9. 页面消息发送失败

每一种错误都应该尽量给出明确提示，别统一写成“统计失败”。

## 15. 第十四步：加入悬浮窗

当 popup 能稳定统计之后，再做悬浮窗。

建议做法：

1. content script 动态创建一个 DOM 容器
2. 注入一段独立样式
3. 把开始日期、结束日期、按钮、状态区、结果区放进去
4. 给它拖拽能力
5. 默认放在搜索栏上方靠右

到 `2.0.0` 时，悬浮窗已经包含：

1. 开始日期
2. 结束日期
3. `上月`
4. `当月`
5. `执行统计`
6. `AI生成日报`
7. 状态提示区
8. 统计结果区
9. AI 提示词区
10. 工时日历区

### 悬浮窗为什么放在 content script

因为它属于业务页面的一部分，必须能直接读页面结构、监听页面变化、操作 iframe。

## 16. 第十五步：给悬浮窗做状态恢复

用户体验要好，就不能刷新一次页面就什么都没了。

所以悬浮窗建议保存：

1. 是否显示
2. 位置
3. 日期输入值
4. 是否收起
5. 最近一次统计结果

刷新页面后：

1. 自动恢复悬浮窗
2. 自动回到“我的日报”
3. 恢复输入和结果

注意一个细节：  
AI 提示词区不建议在刷新后自动展开。刷新后应该只恢复悬浮窗和统计结果，提示词区默认保持隐藏，等用户重新点击 `AI生成日报` 再显示。

## 17. 第十六步：做出勤天数和工时日历

### 出勤天数

核心思路：

1. 从 `日报日期` 列读取日期
2. 用 `Set` 去重
3. 统计唯一日期数

### 工时日历

核心思路：

1. 从解析器返回 `dailyHoursMap`
2. 悬浮窗按月渲染日历
3. 每天显示当日累计工时
4. 按规则上色

颜色规则可以抽成一个小函数，不要写死在 UI 模板里。

到 `2.0.0` 时，日历上色规则还补了一个边界：

1. 查询区间内且不晚于今天的工作日，没有工时则按 `0` 标红
2. 周末 `0` 工时不显示
3. 今天之后的未来日期，即使处于查询区间内，也不要标红

否则用户会误以为未来日期已经缺日报。

## 18. 第十七步：给解析器增加“日报明细”

如果你只做工时统计，前面已经够了。  
但如果你还要做 AI 汇总日报，就必须继续往下做。

这一步不要只返回总数，还要把每条日报都解析出来。

建议动态定位这些列：

1. `项目名称`
2. `日报分类`
3. `分类子项`
4. `日报内容`
5. `用时(H)`
6. `日报日期`

然后把每一行整理成：

```js
{
  reportDate: "2026-03-27",
  projectName: "国际再保险业务平台",
  reportCategory: "03-开发及单元测试",
  reportSubCategory: "A-开发实施",
  reportContent: "...",
  hours: 4
}
```

这样后面不管是 AI 提示词、日历详情，还是导出，都可以复用这份结构化数据。

## 19. 第十八步：新增 AI 提示词模块

建议新建：

- `lib/daily-report-prompt.mjs`

这个模块的职责是：

1. 接收统计结果
2. 把 `reportEntries` 拼成统一提示词
3. 返回一段可直接喂给 AI 的文本

### 提示词规则怎么定

这版提示词不是让 AI 机械复述日报，而是让它生成更像“月报/阶段总结”的成品。

所以提示词里要明确约束：

1. 开头总述只写“本月做了什么”
2. 主题数量不少于 3 个，不多于 8 个
3. 正文强调工作内容、成果、价值、个人贡献
4. 不要在最终月报中出现工时、出勤、考勤、记录条数
5. 单条工时可以传给 AI 用来判断工作重心，但不能写进最终成品
6. 不要把审核状态传给 AI，避免引起误解

## 20. 第十九步：做 AI 按钮的交互规则

这一步不是单纯加一个按钮，而是要把悬浮窗内部规则定死。

### 点击 `执行统计`

应该做：

1. 重新统计
2. 如果工时日历打开，先收起
3. 如果 AI 提示词区打开，先收起并清空，避免残留旧提示词

### 点击 `AI生成日报`

应该做：

1. 如果工时日历打开，先收起
2. 优先复用最近一次统计结果
3. 渲染 AI 提示词区
4. 自动复制提示词

### 页面刷新后

应该表现为：

1. 悬浮窗可恢复
2. 最近一次统计结果可恢复
3. AI 提示词区默认隐藏

## 21. 第二十步：解决悬浮窗样式被业务页面污染

这是前端小白最容易忽略的坑。

content script 插进去的按钮，不是在真空里。  
老系统页面原本的按钮样式、float、padding、line-height 都可能把你的布局冲掉。

最常见现象：

1. 本来想做两行四个按钮，结果页面里显示成三颗按钮挤一行
2. 明明写了统一颜色，但某个按钮背景色不对
3. 看起来代码没问题，但页面渲染就是歪的

### 稳妥做法

1. 给悬浮窗根节点唯一 id
2. 所有样式都从这个 id 开始限定
3. 对按钮补齐基础重置：
   - `appearance: none`
   - `padding`
   - `border`
   - `box-sizing`
   - `float: none`
   - `position: static`
4. 对关键布局和关键背景色，必要时用 `!important`
5. 按钮区直接用明确的两列 grid，不要依赖默认流式布局

## 22. 第二十一步：解决悬浮窗内部滚动

当工时日历展开后，悬浮窗会变得很长。  
如果你只给最外层加一个 `overflow-y: auto`，通常不够。

你要同时解决两件事：

1. 面板内部真的能滚
2. 鼠标滚轮滚的是悬浮窗，不是整个网页

### 推荐实现

1. 悬浮窗根节点做成纵向 flex 容器
2. 头部固定
3. 内容区 `flex: 1` 并允许滚动
4. 动态根据当前面板位置计算可用高度
5. 对内容区的 `wheel` 事件做拦截，优先滚动悬浮窗内容

## 23. 调试时怎么想问题

插件项目调试最重要的是“先定位上下文”。

每次出错先问自己：

1. 出错代码在 popup、background，还是 content script？
2. 当前是不是在顶层页面，还是 iframe 页面？
3. 这个请求是页面发的，还是插件后台发的？
4. 读到的是完整 HTML，还是当前页 DOM？

只要这几个问题答得出来，大部分问题都能解决。

## 24. 你可以照着做的开发顺序

建议你以后自己重做时，严格按这个顺序：

1. 研究页面结构
2. 写离线解析器
3. 写日期工具
4. 搭 manifest、popup、background、content script 骨架
5. 打通 popup -> background -> content script 消息
6. 找到 iframe
7. 自动进入“我的日报”
8. 自动填日期并搜索
9. 等待 iframe 刷新
10. 获取完整 HTML
11. 接入解析器
12. popup 展示结果
13. 做错误提示
14. 做悬浮窗
15. 做状态恢复
16. 做工时日历
17. 让解析器返回日报明细
18. 新建 AI 提示词模块
19. 给悬浮窗接入 `AI生成日报`
20. 处理按钮样式污染
21. 处理悬浮窗内部滚动

不要乱序。乱序开发非常容易把自己绕晕。

## 25. 你自己练手时建议加的功能

如果你想确认自己真的学会了，建议再练 5 个功能：

1. 增加“本周工时”
2. popup 中加入自定义日期范围输入
3. 点击日历某一天后显示当天日志条目
4. 把 host 地址做成可配置
5. 让 AI 提示词支持“日报版”和“月报版”两种输出模式

这 5 个练完，你对这个插件就不是“看懂”，而是真会做了。

## 26. 最后给你的开发原则

### 原则 1：先验证，再抽象

先确认请求和页面行为是对的，再提炼成函数。

### 原则 2：先数据链路，再界面

UI 只是表现层，数据准确才是生命线。

### 原则 3：别假设页面稳定

老系统一定会变，选择器、列顺序、登录态都可能变。

### 原则 4：上下文要非常清楚

每一行代码都要知道自己运行在哪一层。

### 原则 5：错误提示一定具体

“统计失败”没价值。  
“未登录”“没找到 iframe”“当前不是系统主页”才有价值。

### 原则 6：页面内组件一定要防样式污染

content script 插进去的 DOM，不是活在真空里。  
你不主动重置样式，业务页就会替你决定按钮长什么样。

### 原则 7：能复用结果，就不要重复请求

工时日历、AI 提示词、统计结果，都应该尽量基于同一份统计结果对象展开，而不是各自再查一次。
