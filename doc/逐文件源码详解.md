# 逐文件源码详解

这份文档不是“逐行解释”，而是“逐文件源码详解”。

目标是让你建立一种真正可维护的理解方式：

1. 这个文件运行在哪个上下文
2. 这个文件的职责是什么
3. 这个文件和其他文件怎么协作
4. 以后你要改功能时，优先改哪个文件

如果你先把“逐文件关系”理顺，再去看具体代码，理解会快很多。

---

## 一、先建立整体地图

这个插件主要由 9 个核心文件组成：

1. `manifest.json`
2. `popup.html`
3. `popup.css`
4. `popup.js`
5. `background.js`
6. `content.js`
7. `lib/date-range.mjs`
8. `lib/report-parser.mjs`
9. `lib/daily-report-prompt.mjs`

它们可以理解成下面这张图：

```text
用户点击 popup
    ↓
popup.js
    ↓
background.js
    ↓
content.js
    ↓
业务页面 iframe / my_report.jsp
    ↓
完整 HTML 返回
    ↓
background.js 调用 report-parser.mjs
    ↓
background.js 调用 daily-report-prompt.mjs
    ↓
popup.js / content.js 渲染结果
```

所以你读代码时，不要把这些文件当成孤立文件。  
它们是一条完整链路上的不同站点。

---

## 二、`manifest.json` 详解

文件位置：

- `manifest.json`

### 1. 这个文件运行在哪

它不“运行”。  
它是 Chrome 插件的配置总入口，告诉浏览器：

- 这个插件叫什么
- 有什么权限
- popup 是哪个文件
- background 是哪个文件
- content script 要注入到哪些页面

### 2. 关键字段解释

#### `manifest_version`

```json
"manifest_version": 3
```

表示这是 MV3 插件。  
MV3 和老的 MV2 最大区别之一是：

- 后台脚本不再是长期驻留页面
- 而是 service worker

这会影响你的调试方式。

#### `permissions`

当前用了 3 个：

- `activeTab`
- `storage`
- `scripting`

它们分别表示：

- `activeTab`: 可以拿到当前活动标签页
- `storage`: 可以保存最近一次统计结果、悬浮窗状态
- `scripting`: 可以动态给页面注入 `content.js`

#### `host_permissions`

```json
"http://10.19.3.38/*"
```

表示插件被允许操作这个域名下的页面。

如果以后换环境，最先要检查的就是这里。

#### `background`

```json
"background": {
  "service_worker": "background.js",
  "type": "module"
}
```

说明后台入口是 `background.js`，并且它是 ESM 模块，所以可以直接 `import`。

#### `action`

```json
"default_popup": "popup.html"
```

说明点击浏览器工具栏中的插件图标后，会打开 `popup.html`。

#### `content_scripts`

```json
"matches": ["http://10.19.3.38/*"],
"js": ["content.js"]
```

表示只要用户打开了这个域名下的页面，Chrome 就会尝试注入 `content.js`。

### 3. 你以后改功能时，什么时候要改这个文件

以下场景需要改：

1. 内网域名变了
2. 新增权限，比如下载、标签管理
3. popup 文件名改了
4. background 文件名改了
5. content script 匹配范围变了

## 三、`popup.html` 详解

文件位置：

- `popup.html`

### 1. 这个文件运行在哪

运行在插件自己的 popup 小窗口里。

它不是业务页面的一部分，也不能直接操作内网页面的 DOM。

### 2. 它的职责是什么

只负责结构，不负责逻辑。

你可以把它看成 popup 的骨架模板，主要提供：

- 标题
- 作者信息
- 功能说明
- 三个按钮
- 状态区
- 结果区

### 3. 结构怎么理解

#### 标题区

```html
<h1>日报工时统计</h1>
<p class="meta">AUTHOR HXY · power by codex</p>
<p class="hint">...</p>
```

这三行分别负责：

- 产品名
- 作者信息
- 功能简介

#### 操作按钮区

```html
<button id="lastMonthButton">上月工时</button>
<button id="currentMonthButton">当月工时</button>
<button id="openPanelButton">嵌入网页</button>
```

这 3 个 `id` 非常重要，因为 `popup.js` 就是靠它们来绑事件。

#### 结果区

结果区本质是一个 `dl`：

- `dt` 表示字段名
- `dd` 表示字段值

这个结构很适合做“标签 + 数值”的统计展示。

### 4. 你以后改功能时，什么时候要改这个文件

1. popup 按钮文案变了
2. 新增 popup 按钮
3. 结果区要增加字段
4. 标题区文案调整

如果只是改逻辑，不一定要改它。

---

## 四、`popup.css` 详解

文件位置：

- `popup.css`

### 1. 这个文件运行在哪

只作用于 `popup.html`。

不会影响业务页面，也不会影响悬浮窗。

### 2. 它的职责是什么

负责 popup 的视觉表现。

包括：

- 卡片样式
- 按钮样式
- 状态文字颜色
- 结果区排版

### 3. 关键样式区块

#### 根样式

```css
:root { ... }
body { ... }
```

控制 popup 的整体字体、背景、颜色风格。

#### `.card`

这是卡片容器样式。  
你的 popup 目前就是两个卡片：

1. 操作卡片
2. 结果卡片

#### `.actions`

```css
grid-template-columns: repeat(3, 1fr);
```

这里让 3 个按钮等宽排列。

#### `.primary` / `.secondary` / `.ghost`

这 3 个类决定了 3 个按钮的视觉层级：

- 主功能按钮
- 次功能按钮
- 嵌入网页按钮

#### `.status`

这个区域负责显示：

- loading
- error
- warning

所以它是状态反馈层，不是结果层。

### 4. 你以后改功能时，什么时候改这个文件

1. popup 按钮布局变了
2. popup 视觉样式要调整
3. 要新增新的视觉状态

如果只是统计逻辑变化，不用动它。

---

## 五、`popup.js` 详解

文件位置：

- `popup.js`

### 1. 这个文件运行在哪

运行在 popup 页面里。

它的权限比普通网页大，因为它可以调用 Chrome Extension API，比如：

- `chrome.tabs.query`
- `chrome.runtime.sendMessage`
- `chrome.scripting.executeScript`
- `chrome.storage.local`

### 2. 它的职责是什么

它负责 popup 的全部行为逻辑：

1. 绑定按钮事件
2. 获取当前 tab
3. 发起统计
4. 打开悬浮窗
5. 渲染结果
6. 展示状态信息

### 3. 代码结构怎么理解

#### 顶部 DOM 引用

```js
const lastMonthButton = ...
const currentMonthButton = ...
const openPanelButton = ...
```

这部分是先把页面中的按钮、状态区、结果区抓出来，后面复用。

#### `init()`

作用：

1. 给 3 个按钮绑事件
2. 从 `chrome.storage.local` 里恢复最近一次统计结果

这是 popup 的启动入口。

#### `runPreset(preset)`

这是 popup 触发统计的核心函数。

它做了 4 件事：

1. 设置 loading 状态
2. 找当前 tab
3. 向 background 发 `RUN_STATISTICS`
4. 成功后渲染结果，失败后展示报错

这个函数不自己统计，只做“发起请求 + 接收结果”。

#### `openFloatingPanel()`

这个函数不负责绘制悬浮窗，它只是：

1. 找到当前 tab
2. 确保 `content.js` 已经注入
3. 给 content script 发 `SHOW_FLOATING_PANEL`

真正的悬浮窗 DOM 是在 `content.js` 中创建的。

#### `getActiveTab()`

这是个很常见的小工具函数。  
popup 自己不知道当前业务页是谁，所以它先查询当前活动标签页。

#### `renderResult(result)`

负责把 background 返回的数据渲染到 popup 里。

注意它只负责展示，不负责算结果。

#### `sendRuntimeMessageWithTimeout()`

这是一个很实用的封装。

为什么要加超时？

因为如果 background 或页面挂住了，popup 不能一直无响应。  
超时能给用户更明确的反馈。

### 4. 以后你要改 popup 逻辑，优先改哪里

#### 想新增快捷时间按钮

优先改：

1. `popup.html`
2. `popup.css`
3. `popup.js` 的 `init()`

#### 想调整统计结果展示

优先改：

1. `popup.js` 的 `renderResult()`
2. `popup.html`
3. `popup.css`

#### 想让 popup 支持自定义日期

优先改：

1. `popup.html` 新增日期输入框
2. `popup.js` 新增自定义消息发送逻辑

## 六、`background.js` 详解

文件位置：

- `background.js`

### 1. 这个文件运行在哪

运行在 Chrome MV3 的 background service worker 中。

它不是页面脚本，所以：

- 不能直接操作业务页面 DOM
- 但可以和 popup、content script 通信
- 可以调用 Chrome API

### 2. 它的职责是什么

它是整个插件的数据调度中心。

主要职责：

1. 接收统计请求
2. 解析日期范围
3. 确保页面脚本已注入
4. 让 content script 去页面里执行统计
5. 拿回完整 HTML
6. 调用解析器生成结果
7. 保存最近一次统计结果

### 3. 代码结构怎么理解

#### 顶部 import

```js
import { getPresetRange } from "./lib/date-range.mjs";
import { parseWorkHours } from "./lib/report-parser.mjs";
import { buildAiSummaryPrompt } from "./lib/daily-report-prompt.mjs";
```

说明 background 不直接实现日期逻辑、解析逻辑、AI 提示词逻辑，而是把这三块拆成独立模块。

这是很好的分层设计。

#### `chrome.runtime.onMessage.addListener`

这是 background 的主入口。  
它监听 popup 或 content script 发来的消息。

当前只处理一种主消息：

- `RUN_STATISTICS`

#### `handleRunStatistics(message, sender)`

这是真正的核心函数。

它按顺序做：

1. `resolveDateRange()`  
   先确定统计时间。

2. 取 `activeTabId` 和 `activeTabUrl`  
   确认要操作哪个页面。

3. `ensureContentScriptReady(activeTabId)`  
   在消息发送前，确保页面里有 `content.js`。

4. `runPageSearchAndGetHtml(...)`  
   让页面去执行统计，并返回完整 HTML。

5. `parseWorkHours(html)`  
   用解析器把 HTML 变成结构化数据。

6. `buildAiSummaryPrompt(result)`  
   基于结构化数据生成统一的 AI 月报提示词。

7. `chrome.storage.local.set(...)`  
   把结果缓存下来，popup 下次打开可以恢复。

#### `resolveDateRange(message)`

这个函数支持两种输入：

1. `preset`
2. `startDate + endDate`

这就是为什么 popup 和悬浮窗都能共用同一个 background 入口。

#### `runPageSearchAndGetHtml()`

作用是：

1. 给 tab 发消息
2. 让 content script 在页面里执行搜索
3. 拿到完整 HTML

background 自己不接触 DOM。

#### `ensureContentScriptReady()`

这是修复 “Receiving end does not exist” 的关键。

如果不先注入脚本，页面可能根本没有监听器，自然就收不到消息。

#### `normalizeConnectionError()` / `normalizeInjectionError()`

这两个函数的价值不在技术，而在产品体验。

如果直接把 Chrome 底层报错丢给用户，用户看不懂。  
经过翻译后，用户至少知道：

- 是页面没刷新
- 还是当前页不对
- 还是脚本注入失败

### 4. 以后你要改统计链路，优先改哪里

#### 想新增统计入口类型

优先改：

- `handleRunStatistics`

#### 想新增 preset，比如“本周”

优先改：

- `resolveDateRange`
- `lib/date-range.mjs`

#### 想优化错误提示

优先改：

- `normalizeConnectionError`
- `normalizeInjectionError`

## 七、`content.js` 详解

文件位置：

- `content.js`

### 1. 这个文件运行在哪

运行在业务页面里。

这是整个项目里最重要、也最复杂的文件，因为只有它能：

- 访问业务页面 DOM
- 访问 iframe
- 点击页面按钮
- 创建悬浮窗

### 2. 这个文件的职责是什么

它同时负责两条链路：

1. 页面统计链路
2. 悬浮窗链路

你可以把它理解成“页面执行器 + 页面内 UI 组件”。

---

### 3. 第一部分：脚本启动与消息监听

顶部的自执行函数主要干两件事：

1. 防止重复注入
2. 监听 background 发来的消息

当前它处理两类消息：

- `RUN_STATISTICS_IN_PAGE`
- `SHOW_FLOATING_PANEL`

第一类负责“页面里执行统计”。  
第二类负责“显示悬浮窗”。

这就是为什么 background 不用直接碰页面 DOM，popup 也不用直接碰页面 DOM。

---

### 4. 第二部分：页面统计主流程

核心函数是：

- `runStatisticsInPage({ startDate, endDate })`

这是页面统计的总调度。

它的流程是：

1. `findReportContext()`  
   先判断现在在哪个页面状态。

2. 如果是登录页，直接报错。

3. 如果不是日报页，调用 `navigateToMyReport()` 自动切过去。

4. 找到 `#start_time`、`#end_time`、`#search_btn`。

5. 用 `setInputValue()` 填表单。

6. 调用 `submitSearchInIframe()` 真正触发搜索并等待 iframe 刷新。

7. 调用 `fetchFullReportHtml()` 再拿一次完整 HTML。

这里最值得你记住的是：  
“页面刷新”和“拿完整 HTML”是两步，不是一步。

---

### 5. 第三部分：页面状态识别

关键函数：

- `findReportContext()`
- `isReportDocument()`
- `isLoginDocument()`

这部分逻辑的意义是：  
插件不能假设当前 iframe 一定是“我的日报”。

它会把当前状态统一抽象成：

- `report`
- `login`
- `other`

这么做有两个好处：

1. 逻辑判断很清晰
2. 错误提示会更准确

如果以后系统结构变化，你最先要检查的就是这里。

---

### 6. 第四部分：自动进入“我的日报”

关键函数：

- `navigateToMyReport()`
- `clickMyReportLink()`
- `forceNavigateIframeToMyReport()`
- `buildContextFromLoadedDocument()`

设计思路是“双保险”：

1. 优先真实点击左侧链接
2. 点击不到时，直接设置 iframe 的 `src`

这么做的原因是：

- 真实点击更符合页面自身行为
- 直接改 `src` 更稳，是兜底方案

这是一个非常典型的老系统兼容方案。

---

### 7. 第五部分：搜索与等待刷新

关键函数：

- `setInputValue()`
- `triggerSearch()`
- `waitForIframeLoad()`
- `submitSearchInIframe()`

#### `setInputValue()`

它不是只赋值，而是：

1. `focus`
2. 改 `value`
3. 派发 `input`
4. 派发 `change`
5. `blur`

这是为了兼容老页面可能绑定的事件。

#### `triggerSearch()`

触发顺序是：

1. `button.click()`
2. `form.requestSubmit()`
3. `form.submit()`

这种从“更像用户操作”到“更底层”的顺序，兼容性最好。

#### `waitForIframeLoad()`

这个函数很重要，因为按钮点下去不代表结果已经渲染好了。  
它通过监听 `iframe load` 来等待页面刷新完成。

---

### 8. 第六部分：为什么还要 `fetchFullReportHtml()`

这是整个项目的关键点之一。

如果只读取刷新后的表格 DOM，可能只拿到当前页。

所以项目最终做法是：

1. 先让页面真实刷新
2. 再用 iframe 的 `window.fetch` 发同样的 POST
3. 拿完整 HTML

这样才能正确处理前端分页。

如果以后再出现“只统计第一页”，首先就要检查这个函数。

---

### 9. 第七部分：悬浮窗入口链路

关键函数：

- `showFloatingPanelFromMessage()`
- `ensureReportContextForPanel()`

这部分逻辑和统计主流程很像，但它的目标不是“算数据”，而是“先确保页面处于可嵌入悬浮窗的正确状态”。

也就是说：

1. 确认有 iframe
2. 确认没掉登录
3. 如有必要自动进入“我的日报”
4. 再把面板显示出来

---

### 10. 第八部分：悬浮窗 DOM 创建

关键函数：

- `ensureFloatingPanel()`
- `ensureFloatingPanelStyles()`

#### `ensureFloatingPanel()`

这就是面板的工厂函数。

它会：

1. 确保样式已注入
2. 如果面板已存在，直接复用
3. 如果不存在，就动态创建 DOM
4. 收集按钮和输入框引用
5. 生成统一状态对象 `floatingPanelState`

这里用了一个非常重要的模式：

- 单例模式

面板只能有一个，避免重复插入。

#### `ensureFloatingPanelStyles()`

这个函数把面板样式直接插入页面。

这样做的好处是：

1. 不依赖外部 CSS 文件
2. 样式作用域可控
3. 更适合 content script 动态插入组件

---

### 11. 第九部分：悬浮窗事件系统

关键函数：

- `bindFloatingPanelEvents()`
- `toggleFloatingCollapse()`
- `enableFloatingPanelDragging()`
- `showFloatingPanel()`
- `hideFloatingPanel()`

这部分负责悬浮窗的交互行为：

1. 上月按钮
2. 当月按钮
3. 执行统计
4. AI 生成日报
5. 收起
6. 关闭
7. 工时日历展开/收起
8. AI 提示词复制
9. 鼠标拖拽
10. 面板内部滚动

其中最值得学习的是：

#### 拖拽实现

逻辑是：

1. `mousedown` 记录鼠标和面板的偏移
2. `mousemove` 更新位置
3. `mouseup` 结束拖拽并持久化位置

这是最典型的原生拖拽实现方式。

#### `positionFloatingPanel()`

这个函数不是简单把面板固定在页面右上角，而是：

1. 找搜索表单位置
2. 算出 iframe 在顶层页面中的位置
3. 把面板尽量放在搜索行上方靠右
4. 尽量不挡住搜索区域

这体现的是“页面嵌入式 UI”的布局思路。

---

### 12. 第十部分：悬浮窗内部统计链路

关键函数：

- `applyFloatingPreset()`
- `runFloatingPanelStatistics()`
- `renderFloatingPanelResult()`
- `setFloatingPanelStatus()`
- `setFloatingPanelLoading()`

它和 popup 的统计链路类似，但差别在于：

1. 日期来自悬浮窗输入框
2. 结果渲染到页面面板里
3. 统计前如果日历展开，会先自动收起
4. 统计前如果 AI 提示词区已展开，会先收起并清空

注意：

悬浮窗不自己解析 HTML。  
它依然通过 `chrome.runtime.sendMessage` 调 background，然后复用同一套统计链路。

这就是“一个数据链路，两个展示层”。

### 12.1 AI 提示词链路

`2.0.0` 新增了另一条页面内链路：

1. 用户点击 `AI生成日报`
2. 如果工时日历已展开，先收起
3. 优先复用最近一次统计结果
4. 从统计结果里的 `aiSummaryPrompt` 取出提示词
5. 渲染提示词区
6. 自动复制提示词

这里最关键的设计点是：

1. 悬浮窗不自己拼提示词，而是复用 background 统一生成的结果
2. AI 提示词区默认隐藏，只有用户点击时才显示

---

### 13. 第十一部分：工时日历

关键函数：

- `toggleFloatingCalendar()`
- `setFloatingCalendarExpanded()`
- `renderFloatingCalendar()`
- `buildCalendarMonths()`
- `renderCalendarMonth()`
- `renderCalendarBadge()`

#### 它的数据来源

不是重新请求接口。  
而是直接使用最近一次统计结果中的：

- `dailyHoursMap`

#### 它的逻辑结构

1. 先确定展示哪些月份
2. 再逐月渲染
3. 每个月里按日期渲染格子
4. 每个格子再决定是否显示工时 badge

#### 颜色规则

- 工作日 8 小时：绿色
- 工作日其他工时：红色
- 工作日没有记录：按 0 显示红色
- 周末 0 小时：不显示
- 周末有工时：红色
- 今天之后的未来工作日：不标红

这里最关键的是：

工时日历只是展示层，真正的每日工时聚合在解析器里完成。

### 14. 第十二部分：悬浮窗状态恢复

关键函数：

- `restoreFloatingPanelOnLoad()`
- `persistCurrentFloatingPanelState()`
- `persistFloatingPanelState()`

这部分负责刷新后恢复。

保存的状态包括：

1. 是否可见
2. 开始日期
3. 结束日期
4. 是否收起
5. 是否展开日历
6. 最近一次统计结果
7. 面板位置

所以刷新页面后，用户看到的是“几乎无损恢复”的悬浮窗，而不是每次都从零开始。

但 `2.0.0` 有一个例外需要记住：

- AI 提示词区不会在刷新后自动展开

因为它属于一次性使用结果，默认隐藏更符合用户预期。

## 九、`lib/daily-report-prompt.mjs` 详解

文件位置：

- `lib/daily-report-prompt.mjs`

### 1. 这个文件运行在哪

它是纯字符串拼装模块。  
目前主要由 `background.js` 和 `lib/report-service.mjs` 调用。

### 2. 它的职责是什么

把统计结果里的：

1. 结构化日报明细
2. 时间范围
3. 提示词规则

拼成一段统一的 AI 提示词。

### 3. 为什么要单独拆这个文件

因为 AI 提示词不是页面样式，也不是 HTML 解析逻辑，它有自己独立的规则：

1. 开头总述只写“本月做了什么”
2. 主题数限制为 3 到 8 个
3. 强调成果、价值、个人贡献
4. 单条工时只用于判断工作重心，不写进最终成品
5. 不传审核状态

如果把这套规则塞进 `content.js`，以后会很难维护。

## 十、`lib/report-parser.mjs` 详解

文件位置：

- `lib/report-parser.mjs`

### 1. 这个文件运行在哪

它是纯解析模块。  
目前主要由 `background.js` 调用。

### 2. 它的职责是什么

这是整个项目最核心的数据层。

它负责把 `my_report.jsp` 返回的 HTML 变成结构化统计结果。

具体包括：

1. 判断是否为空 HTML
2. 判断是否是登录页
3. 找到结果表格
4. 动态定位 `用时(H)` 列
5. 动态定位 `日报日期` 列
6. 统计总工时
7. 统计记录数
8. 统计出勤天数
9. 聚合每日工时
10. 处理异常工时
11. 提取 `reportEntries` 供 AI 汇总和后续扩展复用

### 3. 代码结构怎么理解

#### `parseWorkHours(html)`

这是总入口。

它会先做输入校验，再优先使用 `DOMParser` 解析。  
如果当前环境没有 DOMParser，就回退到正则方案。

这说明解析器不是“只在浏览器里能用”的脆弱代码，而是有一定环境兼容性的。

#### `parseTableWithDom(document)`

这是主解析路径。

它做的关键事情有：

1. 找 `#maintable`
2. 从表头中找列索引
3. 遍历 `tbody tr`
4. 累加工时
5. 统计行数
6. 把日报日期放进 `Set`
7. 把每日工时累加到 `Map`

你要特别注意这里的设计：

- 工时统计用 `totalHours`
- 出勤天数用 `Set`
- 工时日历用 `Map`

这 3 个数据结构分别解决不同问题。

#### `parseWithRegex(html)`

这是兜底路径。

正常情况下你可能用不到它，但保留它的好处是：

1. 纯字符串环境也能跑
2. DOM 解析失败时还有备份

#### `buildResult(...)`

把中间过程里的各种聚合变量统一封装成最终结果对象。

这一步非常重要，因为它定义了“整个插件的统计数据标准结构”。

当前返回的核心字段有：

- `totalHours`
- `rowCount`
- `attendanceDayCount`
- `dailyHoursMap`
- `reportEntries`
- `invalidHourCount`
- `invalidHourSamples`
- `warning`

#### `findHoursColumnIndex()` / `findReportDateColumnIndex()`

这是动态找列，而不是写死列号。

这是解析器稳定性的关键。

#### `parseHourValue()`

这个函数只负责一件事：

- 把工时单元格里的文本安全地转成数字

如果是空值，返回“空但不报错”；  
如果是非法字符串，返回“无效并计数”。

这种区分很重要。

#### `isLoginDocument()` / `looksLikeLoginPage()`

这是为了避免未登录时误把登录页当日报页去解析。

如果没有这层判断，用户会看到很迷惑的“未找到表格”。

### 4. 以后你要改统计口径，优先改哪里

#### 想新增统计字段

优先改：

- `parseTableWithDom`
- `parseWithRegex`
- `buildResult`

#### 想改工时规则

优先改：

- `parseHourValue`

#### 想适配表格结构变化

优先改：

- 列查找逻辑
- `#maintable` 的定位逻辑

## 十二、最后给你的真正读码方法

以后你看这个项目里的任何文件，都先回答 4 个问题：

1. 这个文件运行在哪个上下文？
2. 这个文件的输入来自哪里？
3. 这个文件的输出交给谁？
4. 这个文件只负责什么，不负责什么？

例如：

### `popup.js`

- 运行在 popup
- 输入来自用户点击和本地缓存
- 输出交给 background 和 popup DOM
- 负责展示，不负责真正操作 iframe

### `background.js`

- 运行在 service worker
- 输入来自 popup/content script 消息
- 输出交给 content script 和 popup
- 负责调度，不负责直接改页面 DOM

### `content.js`

- 运行在业务页
- 输入来自 background 消息和页面本身
- 输出交给 background、页面 DOM、悬浮窗
- 负责执行和嵌入，不负责最终数据聚合规则定义

### `report-parser.mjs`

- 运行在解析层
- 输入是 HTML 字符串
- 输出是结构化统计结果
- 负责算数据，不负责页面交互

只要你把这 4 个问题答清楚，这个项目你就不只是“看懂了一部分”，而是真的掌握了。
