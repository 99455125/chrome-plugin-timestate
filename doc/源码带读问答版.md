# 源码带读问答版

这份文档不是继续讲“项目概览”，而是像老师带你读源码一样，按真实执行顺序问一个问题、答一个问题。

最适合的阅读方式是：

1. 左边打开这份文档
2. 右边打开对应源码文件
3. 按顺序看

建议你先从 popup 入口开始，再一路跟到 background、content script、解析器。

### 问题 3：`init()` 做了什么？

### 问题 5：`runPreset()` 为什么不直接算结果？

看这里：

- [popup.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/popup.js#L24)

`runPreset()` 的职责是：

1. 切换 loading 状态
2. 获取当前标签页
3. 发消息给 background
4. 拿结果后展示

它不直接操作业务页面，也不解析 HTML。

这说明 popup 只是前台控制器，不是业务执行器。

这是你读插件代码时最重要的意识之一：

- popup 负责“发起”
- 不是“执行”

### 问题 14：为什么 background 还要拿 `activeTabId`？

因为 background 自己不在页面里。  
它要知道“命令要发给哪一个 tab”。

看这里：

- [background.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/background.js#L21)

```js
const activeTabId = message.activeTabId ?? sender?.tab?.id;
```

这行代码很聪明，支持两种调用来源：

1. popup 显式传 `activeTabId`
2. content script 自己发来时，从 `sender.tab.id` 拿

这就是为什么同一个 `RUN_STATISTICS` 可以被 popup 和悬浮窗共用。

### 问题 20：为什么开头要判断 `window.__workHoursStatsContentScriptLoaded`？

看这里：

- [content.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/content.js#L2)

这是防止重复注入。

因为 background 或 popup 可能多次 `executeScript`，如果每次都重复注册监听器、重复插入面板，会出很多怪问题。

所以它先做：

1. 如果已经注入过，就直接返回
2. 如果没有，打一个全局标记

这是 content script 常见的幂等写法。

### 问题 24：`findReportContext()` 到底解决了什么问题？

看这里：

- [content.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/content.js#L91)

1. 页面里有没有主 iframe
2. iframe 当前内容是否可访问
3. iframe 当前到底是什么页面

这一步把“混乱页面状态”统一抽象成一个结构化结果。

这是一种很重要的工程思想：

先把环境识别清楚，再做操作。

---

### 问题 25：为什么这里要特别识别登录页？

因为未登录时最容易误判。

顶层主页可能还在，但 iframe 里已经变成登录页了。  
如果不先识别登录页，就会把登录页错当日报页去操作，最后报出一堆不准确错误。

所以这里的逻辑是：

1. 优先识别 login
2. 再识别 report
3. 否则归为 other

### 问题 30：为什么页面明明已经刷新了，还要 `fetchFullReportHtml()`？

看这里：

- [content.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/content.js#L300)

- 防前端分页

- 页面刷新是为了用户体验
- 二次 fetch 是为了数据完整

### 问题 33：为什么优先用 DOMParser，不直接正则？

看这里：

- [lib/report-parser.mjs](/Users/piaochongmogu/VscodeProjects/chrome-plugin/lib/report-parser.mjs#L11)

1. 更稳定

3. 不容易被 HTML 细节打坏

### 问题 34：解析器为什么要动态找 `用时(H)` 和 `日报日期`？

- [lib/report-parser.mjs](/Users/piaochongmogu/VscodeProjects/chrome-plugin/lib/report-parser.mjs#L36)

- 第几列是工时
- 第几列是日期

这样页面以后如果加列、调列顺序，插件还更稳。

这就是“抗结构变化”的设计。

### 问题 37：为什么解析器要保留 `invalidHourCount`？

## 第五部分：回到悬浮窗

### 问题 38：悬浮窗为什么也不自己算统计？

看这里：

- [content.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/content.js#L955)

悬浮窗内部的“执行统计”最终也是：

```js

  type: "RUN_STATISTICS",
  ...
})
```

也就是说，悬浮窗和 popup 共享同一条后台统计链路。

这样做的好处很大：

1. 逻辑统一
2. 不会一边修 popup，一边忘了修悬浮窗
3. 数据结构保持一致

### 问题 39：为什么工时日历不重新请求接口？

看这里：

- [content.js](/Users/piaochongmogu/VscodeProjects/chrome-plugin/content.js#L1071)

因为工时日历展示的是：

- 当前这次统计结果

而当前这次统计结果里已经有：

- `dailyHoursMap`

所以日历只是把已有数据渲染出来，不需要再请求。

这是一种很典型的前端思路：

- 先算出标准结果
- 再用多个视图展示同一份结果

### 问题 40：为什么刷新页面后悬浮窗还能恢复？

1. 自动确保回到“我的日报”

3. 恢复位置
4. 恢复最近结果
5. 恢复工时日历状态

这就是状态持久化的实际效果。

## 第八部分：2.0.0 版本新增问答

### 问题 41：为什么后来又新增了 `lib/daily-report-prompt.mjs`？

因为“AI 月报提示词”本质上不是页面样式，也不是 HTML 解析逻辑，而是一套独立的规则系统。

它负责：

1. 接收结构化日报明细
2. 约束 AI 输出“本月做了什么”的总述
3. 限制主题数为 3 到 8 个
4. 要求突出成果、价值、个人贡献
5. 禁止把工时、出勤、考勤写进最终月报

如果把这些规则塞进 `content.js`，后面会很难维护。

### 问题 42：为什么 AI 提示词区默认不自动恢复？

因为它和“统计结果”不是同一种东西。

统计结果属于页面状态，刷新后恢复是合理的。  
但 AI 提示词更像一次性操作结果，刷新后默认隐藏更符合用户预期。

所以当前设计是：

1. 刷新后恢复悬浮窗
2. 恢复最近一次统计结果
3. AI 提示词区默认隐藏
4. 只有再次点击 `AI生成日报` 才重新展开

### 问题 43：为什么四个按钮明明写成两行，页面里却可能挤成一行？

因为 content script 插进去的 DOM 会被业务页面原有 CSS 影响。

所以后来做了两层加固：

1. 悬浮窗样式全部挂在唯一 id 作用域下
2. 对按钮补齐 `appearance`、`padding`、`float`、`position` 等重置，并对关键布局使用明确 grid

这不是“为了好看”，而是为了不被老系统页面样式冲掉。

### 问题 44：为什么后来还要单独修滚轮事件？

因为“内容区能滚”和“鼠标滚轮真的滚它”不是一回事。

如果只写了 `overflow-y: auto`，很多时候滚轮事件还是会继续冒泡给网页，最后表现成：

1. 悬浮窗看起来被截断
2. 鼠标一滚，滚的是整个网页

所以 `2.0.0` 又补了：

1. 悬浮窗根节点和内容区的动态高度约束
2. 内容区的 `wheel` 事件拦截

这样工作日历展开后，用户才能在悬浮窗内部真正上下滚动。
